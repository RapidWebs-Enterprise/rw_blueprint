## Research Summary: Declared-vs-Actual Reconciliation and Control-Loop Patterns

**Source**: Kubernetes controller/reconcile-loop documentation; drift-detection tooling (driftctl, tfdrift, driftguard); reference code cloned to `~/.references/tfdrift` and `~/.references/driftguard`
**Date**: 2026-08-27
**Research Category**: Infrastructure Research
**Focus**: The theoretical and practical patterns for reconciling a declared source-of-truth model against observed live state, and classifying the resulting drift

### Key Findings

#### The Kubernetes reconcile loop is the theoretical heart of the problem

The declared-vs-actual problem has a canonical, battle-tested solution in the Kubernetes controller model. Its core principles transfer directly to `rw_blueprint`:

1. **Declared state vs. observed state separation** — Kubernetes splits every object into `.spec` (what you *want*) and `.status` (what *is*). The controller's entire job is to drive `.status` toward `.spec`. This is exactly the `topology.yaml` (declared) vs. `live_state` (observed) split.

2. **Level-triggered, not edge-triggered** — the reconcile loop is *level-triggered*: it runs against the *current* full state, not against a stream of individual events. This is why a missed event is not a missed reconciliation — the next loop pass catches it. This is the argument for **pull (collectors) as the reconciliation baseline**, with push (events) as an optimization, not a requirement.

3. **Idempotency** — a reconcile pass must be safe to run repeatedly with no side effects. This is why probes are **read-only by construction**: observing state must never mutate it.

4. **Convergence, not transaction** — the loop does not guarantee a single atomic fix; it guarantees *eventual* convergence toward declared state. Drift detection is therefore a *continuous* process, not a one-shot.

#### The three-way drift classification is universal

Every drift tool surveyed converges on the same three-way classification, which maps directly to the `reconcile` command's output contract:

| Category | Meaning | tfdrift | driftguard | rw_blueprint |
|----------|---------|---------|------------|--------------|
| **Missing** | declared but not observed | resource absent | `missing` | declared service not running |
| **Extra** | observed but not declared | unmanaged resource | `extra` | unplanned container (Ergo IRC) |
| **Mismatched** | both exist, values differ | attribute diff | `drifted` | port/image/managed_by differs |

This three-way split is what makes the "unplanned service" problem (Ergo, SeaweedFS, Paperclip) *mechanically detectable* rather than manually discovered.

#### Severity classification is a first-class concern

Both reference projects classify drift by severity, not just by type. `tfdrift` assigns severity levels to drift entries; `driftguard` has a dedicated *scorer* stage in its engine pipeline. The severity signal is what the eventual agent uses to decide "auto-fix" vs. "escalate":

- **Low** — cosmetic, reversible, single-service (e.g., a label mismatch)
- **Medium** — functional, reversible (e.g., a port changed)
- **High** — network-partition risk, needs a maintenance window
- **Critical** — data loss / lockout / security breach potential

#### The driftguard engine pipeline is the reference architecture

`driftguard` (cloned to `~/.references/driftguard`) implements the full loop as a staged pipeline, which is the cleanest reference for `rw_blueprint`'s `reconcile` command:

```
parser → collector → analyzer → scorer → patchgen
```

- **parser** — loads the declared model
- **collector** — gathers live state (the probe layer)
- **analyzer** — diffs declared vs. live (the three-way classification)
- **scorer** — assigns severity
- **patchgen** — proposes remediation (the human-in-the-loop PR)

This maps almost one-to-one onto `rw_blueprint`'s target: `validate` (parser) → probes (collector) → `reconcile` (analyzer + scorer) → agent-proposed YAML diff (patchgen).

#### tfdrift's structured report is the output contract reference

`tfdrift` (cloned to `~/.references/tfdrift`) demonstrates the *output* side: drift reports emitted as structured JSON/Markdown/CSV, with ignore rules and a watch mode. The key takeaway for `rw_blueprint`:

- The drift report must be **machine-readable** (JSON) first, human-readable (Markdown) second — because the agent consumes the JSON, and the human reviews the Markdown.
- **Ignore rules** are essential — not every drift is actionable, and a noisy reconciler is a reconciler nobody trusts.

#### The `.spec`/`.status` split implies a live-state schema

The single most important design consequence: because declared and observed state are *different things*, they need *different documents* — but they must share a vocabulary. The live-state schema is a **projection** of the topology schema (a subset of its entities), not a parallel schema. This is what makes diffing trivial and keeps the agent reasoning against one vocabulary.

### Implications for rw_blueprint

1. Add a **`reconcile`** command as the third verb (alongside `validate` and `generate`).
2. Adopt the **three-way drift classification** (missing/extra/mismatched) as the canonical output.
3. Add **severity** as a first-class field on every drift entry.
4. Emit drift reports as **JSON (machine) + Markdown (human)**.
5. Support **ignore rules** to keep the reconciler trustworthy.
6. Design the **live-state schema as a projection** of the topology schema.
