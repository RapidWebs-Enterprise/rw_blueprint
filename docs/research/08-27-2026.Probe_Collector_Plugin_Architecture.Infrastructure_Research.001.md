## Research Summary: Probe/Collector Plugin Architecture for Live-State Observation

**Source**: Python plugin-system research (pluggy vs. stevedore); osquery host-introspection model; reference code cloned to `~/.references/tfdrift` and `~/.references/driftguard`
**Date**: 2026-08-27
**Research Category**: Infrastructure Research
**Focus**: How to structure the "pull" side of the observation loop — a registry of read-only probes that each emit a fragment of live state

### Key Findings

#### The probe is the unit of observation

Each probe is a small, self-contained collector that observes one aspect of the infrastructure and emits a fragment of live state. The registry maps probe → what it observes → what it emits:

| Probe | Observes | Emits |
|-------|----------|-------|
| `incus` | `incus list` | nodes (containers), their state |
| `podman` | `podman ps` | services (running workloads, images, ports) |
| `port` | `ss -tlnp` | links (open ports → connectivity) |
| `dns` | `dig`/`kdig` | DNS resolution health |
| `tailscale` | `tailscale status` | mesh peers (links) |

#### Probes are read-only by construction

The single most important safety property: **a probe never mutates state, it only observes**. This is what makes probes safe to run on a heartbeat with no human-in-the-loop. The read-only constraint is enforced by design (probes only invoke read commands) and by convention (no probe is given write access to anything).

This maps directly to the RWDN recovery roadmap's autonomy surface: read-only diagnostics = auto; anything mutating = HITL.

#### The osquery model is the reference for host introspection

osquery is the canonical "SQL over the host" model: it exposes the entire host as a set of virtual tables (`processes`, `listening_ports`, `routes`, `users`) that can be queried declaratively. The transferable insight for `rw_blueprint`:

- **Declarative observation** — you describe *what* you want to observe, not *how* to collect it. The probe abstracts the collection mechanism.
- **Uniform output shape** — every osquery table returns rows with a consistent schema, regardless of the underlying source. This is the same "normalized fragment" contract the probe registry needs.
- **Composability** — probes can be combined (a `port` probe + a `podman` probe together answer "what service is listening on what port").

#### Plugin systems: pluggy vs. stevedore

Two mature Python plugin systems were evaluated for the probe registry:

| System | Model | Fit |
|--------|-------|-----|
| **pluggy** | hook-based (pytest's engine) | Strong for *extension points* (callbacks), weaker for *discovery* of independent collectors |
| **stevedore** | entry-point-based (OpenStack) | Strong for *discovery* of independent plugins via `entry_points` |

For a probe registry, the requirement is **discovery of independent collectors** — each probe is a self-contained unit that registers itself and can be enumerated. This favors the **entry-point / registry pattern** (stevedore-style) over the hook pattern (pluggy-style). However, for a fleet this small (5 probes), a **simple in-process registry** (a dict of probe-name → callable, or a `Probe` base class with auto-registration) is sufficient and avoids a plugin-framework dependency.

#### The registry pattern (recommended)

The pragmatic sweet spot is a **`Probe` base class with a registry**, not a full plugin framework:

```python
class Probe:
    name: str  # "podman"
    observes: str  # "services"

    def collect(self) -> LiveStateFragment: ...
```

Probes register themselves (via a decorator or a module-level registry), and the reconciler enumerates the registry to run all probes. This gives:

- **Discoverability** — `rw-blueprint probes list` enumerates what's available.
- **Extensibility** — adding a probe is adding a module, not modifying the engine.
- **No framework dependency** — a dict is enough for 5 probes; a framework is premature.

#### Probe output must be a normalized fragment

Every probe emits into the *same* normalized shape (the live-state schema projection). This is the contract that makes the reconciler's diff trivial: if every probe emits `nodes`/`services`/`links` in the same vocabulary as `topology.yaml`, then diffing is a mechanical comparison, not a per-probe bespoke transform.

#### Failure isolation

A probe that fails (e.g., `incus` not installed on a host) must not take down the whole reconciliation. Each probe runs in isolation, and a probe failure is recorded as a *probe error* (distinct from drift), not as a crash. This is the "partial results under failure handling" principle.

### Implications for rw_blueprint

1. Implement a **`Probe` base class + registry** (in-process, no framework dependency).
2. Ship the **five core probes** (incus, podman, port, dns, tailscale) as the initial set.
3. Enforce **read-only** as a hard constraint on every probe.
4. Emit **normalized fragments** into the live-state schema projection.
5. Add a **`probes list`** command for discoverability.
6. **Isolate probe failures** — a failed probe is a probe error, not a crash.
