## Research Summary: Reference Projects for the Reconcile / Drift-Detection Layer

**Source**: GitHub repositories cloned to `~/.references/` for implementation reference
**Date**: 2026-08-27
**Research Category**: Infrastructure Research
**Focus**: Two Python projects that strike at the conceptual heart of the reconcile/drift-detection layer, cloned for reference during implementation

### Key Findings

#### Two projects were selected and cloned

Both are Python (matching the `rw_blueprint` stack), both are directly on-target for the reconcile/drift-detection layer, and both are substantive (not empty shells). They were cloned with `--depth 1` to `~/.references/`.

| Project | Repo | License | Python | What it demonstrates |
|---------|------|---------|--------|----------------------|
| **tfdrift** | `sudarshan8417/tfdrift` | Apache-2.0 | 3.9+ | Drift detection CLI, structured reports, severity, watch mode, ignore rules |
| **driftguard** | `EdwinJdevops/driftguard` | MIT | 3.12 | Full drift engine pipeline (parser→collector→analyzer→scorer→patchgen), HITL PR remediation |

#### tfdrift — the closest match to the `reconcile` command

`tfdrift` (v0.5.3) is a Python CLI that detects drift between Terraform state and live infrastructure. Its features map almost one-to-one onto `rw_blueprint`'s target `reconcile` command:

| tfdrift feature | rw_blueprint equivalent |
|-----------------|-------------------------|
| Structured drift reports (JSON/Markdown/CSV/table) | `reconcile` output (JSON machine + Markdown human) |
| Severity classification (critical/high/medium/low) | severity field on every drift entry |
| Watch mode (continuous monitoring) | the eventual push/watchdog layer |
| Ignore rules (`.tfdriftignore`) | ignore rules to keep the reconciler trustworthy |
| CI/CD friendly (exit codes, JSON) | machine-readable output for the agent |

**Reference value**: its `detectors/drift.py` (the diff logic) and `models.py` (the declared-vs-observed model separation) are the concrete patterns to study for the `reconcile` implementation.

#### driftguard — the closest match to the "agent proposes, human approves" model

`driftguard` is a Python/FastAPI system that compares `terraform.tfstate` against live AWS state, scores every discrepancy against CIS AWS Benchmarks and MITRE ATT&CK, and opens a GitHub PR with a suggested patch — **for a human to review, not to auto-merge**. This is exactly the HITL remediation model `rw_blueprint` targets.

Its engine is a staged pipeline:

```
parser → collector → analyzer → scorer → patchgen
```

| Stage | Role | rw_blueprint equivalent |
|-------|------|-------------------------|
| parser | load declared model | `validate` (schema parse) |
| collector | gather live state | probe registry |
| analyzer | diff declared vs. live | `reconcile` (three-way classification) |
| scorer | assign severity/score | severity field |
| patchgen | propose remediation | agent-proposed YAML diff (HITL) |

**Reference value**: its `engines/drift.py` (the analyzer) and `models/models.py` (the declared-vs-observed model separation) are the concrete patterns to study for the pipeline architecture.

#### The shared architectural insight

Both projects independently converge on the same two principles that `rw_blueprint` has already adopted:

1. **Declared model and observed state are distinct types**, compared by a dedicated diff stage.
2. **Remediation is proposed, not auto-applied** — the human (or agent, HITL-gated) reviews the diff before it lands.

This convergence is strong independent validation that the `rw_blueprint` reconcile/probe/watchdog design is on the right architectural track.

#### What these projects do NOT provide (the gap rw_blueprint fills)

Both are **Terraform/AWS-specific**. They assume a Terraform state file as the declared source and AWS as the live source. `rw_blueprint`'s gap is:

- **Provider-agnostic** — the declared model is a generic `topology.yaml`, not Terraform state.
- **Agent-readable canonical model** — the YAML is the *objective reality* an LLM agent reasons against, not just a drift-detection input.
- **Incus/podman/Tailscale/DNS** — the RWDN stack, not AWS.

So the reference projects inform the *mechanics* (diff logic, severity, pipeline, HITL remediation), while `rw_blueprint` supplies the *generic, agent-readable, RWDN-native* model.

### Implications for rw_blueprint

1. Study `tfdrift`'s `detectors/drift.py` + `models.py` for the diff and model-separation patterns.
2. Study `driftguard`'s `engines/drift.py` + `models/models.py` for the pipeline and HITL-remediation patterns.
3. Adopt the **three-way classification + severity + ignore rules** that both projects share.
4. Keep `rw_blueprint` **provider-agnostic and agent-readable** — the gap these projects don't fill.
