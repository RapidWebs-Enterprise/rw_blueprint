## Research Summary: Landscape Survey of YAML Source-of-Truth Topology and Diagram Generation Tools

**Source**: Web research via Exa search (Marrow, Shumoku, TopoViewer, Archyl, diagrams-as-code, Terravision, StackMap, InfraMap, NetBox, Nautobot, Infrahub, Device42, Itential, Prajwal Ravi)  
**Date**: 2026-08-27  
**Research Category**: Infrastructure Research  
**Focus**: Survey of existing tools that treat a structured model (YAML or IaC state) as the source of truth and generate topology diagrams, documentation, or IaC from it

### Key Findings

#### The pattern is real, mature, and splits into three tiers

The "declare a structured model → engine generates artifacts" pattern is well-established. The surveyed tools fall into three distinct architectural tiers, distinguished by *what* is the source of truth and *what* is generated.

| Tier | Pattern | Representative tools | Source of truth | Generated output |
|------|---------|---------------------|-----------------|------------------|
| **A — Diagram-as-code** | YAML *is* the SoT | Marrow, Shumoku, TopoViewer, Archyl, diagrams-as-code (awslabs) | Hand-authored YAML | Interactive HTML/SVG diagrams, docs, ADRs |
| **B — IaC-as-source** | Terraform/state *is* the SoT | Terravision, StackMap, InfraMap, infra-diagram-cli | Terraform HCL / tfstate | Provider-aware diagrams, drift detection |
| **C — Full SoT platforms** | Database *is* the SoT | NetBox, Nautobot, Infrahub, Device42 | Structured DB (IPAM/DCIM) | Diagrams, API, automation |

#### Tier A is the correct fit for this project

Tier A is the right choice for `rw_blueprint` for three reasons:

1. **No Terraform dependency** — the RWDN is not yet IaC-managed (IaC tool choice is an open decision). Tier B tools require Terraform state that does not exist yet.
2. **Agent-readability** — YAML is trivially parseable and generatable by LLMs, which is the core "objective reality" requirement.
3. **Low ceremony** — Tier C platforms (NetBox et al.) carry 15–25% manual-entry overhead and a heavyweight database, disproportionate to a fleet of one Hetzner host + three system containers + ~six services.

#### Tier A tool-by-tool assessment

| Tool | What it does | Relevance to rw_blueprint |
|------|-------------|---------------------------|
| **Marrow** | Topology YAML → self-contained interactive HTML; "declare structure, not layout"; ships a Claude Code skill | Closest to the vision; but output is HTML, not an agent-readable canonical model |
| **Shumoku** | YAML/NetBox/LLDP/SNMP → SVG/HTML topology; 900+ vendor icons; live weathermap | Strong rendering; heavier; multi-source ingestion |
| **TopoViewer** | `topology.yaml` + `stylesheet.yaml` + `mapper.yaml` → interactive diagrams (React/MkDocs/Grafana) | Clean separation of model / presentation / telemetry |
| **Archyl** | Single `archyl.yaml` → full C4 model + diagrams + ADRs, synced via CI/CD | Good for the "docs" half; C4-centric |
| **diagrams-as-code** (awslabs) | YAML → diagrams, Go CLI, MCP server | AWS-centric; Go, not Python |

#### Two findings that settle the design philosophy

1. **Prajwal Ravi, "Network Topology as Code"** — the exact philosophy this project embodies, stated independently: *"A structured YAML topology is something an agent can reason about, query, and generate modifications for. Ask an agent to 'add a new VLAN' and it can produce the exact YAML diff. Try that with a Visio diagram."* This confirms the "objective reality" requirement.

2. **Itential source-of-truth research** — *60% of documentation projects fail, and accuracy degrades to 15–30% within 30–60 days without automation.* This quantifies the drift problem that motivated the project: hand-written markdown files describing the same system inevitably disagree.

#### Architectural conclusion

The surveyed Tier A tools are all *renderers* — they produce human-facing diagrams. None cleanly provides the *agent-readable canonical model* that is the primary requirement. The correct architecture is therefore:

- **Keep the YAML schema as the language-agnostic contract** (the canonical source of truth).
- **Build a thin in-house engine** (Python) that validates and emits artifacts.
- **Optionally bolt a Tier A renderer** (Marrow/Shumoku) on later as a *presentation backend*, without touching the model.

This is a rebuild of tooling that existed before the RWDN data loss, but cleaner and standards-conformant from day one.
