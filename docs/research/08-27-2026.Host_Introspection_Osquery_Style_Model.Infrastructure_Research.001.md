## Research Summary: Host Introspection (osquery-style) as the Probe Model

**Source**: osquery architecture documentation (Kolide "Under the Hood", osquery.io, osquery.readthedocs.io); OpenTelemetry Collector agent-vs-gateway patterns; Uptycs "osquery in-house vs building"
**Date**: 2026-08-27
**Research Category**: Infrastructure Research
**Focus**: Whether `rw_blueprint`'s probe layer should adopt osquery itself, or borrow its *model* (declarative observation, virtual tables, event publishers) into a lightweight in-house collector

### Key Findings

#### osquery's core model: the OS as a relational database

osquery exposes the operating system as a high-performance relational database. SQL tables represent abstract concepts — running processes, open sockets, listening ports, loaded kernel modules, file hashes. The transferable insight is the *model*, not the SQL:

- **Declarative observation** — you describe *what* you want to observe (`SELECT * FROM processes`), not *how* to collect it. The collection mechanism is abstracted behind the table.
- **Uniform output shape** — every table returns rows with a consistent schema, regardless of the underlying source (file parse, system API, event buffer).
- **Composability** — tables can be `JOIN`ed (a `processes` table joined with a `process_open_sockets` table answers "what process is listening on what port").

This is the same "normalized fragment" contract the `rw_blueprint` probe registry needs — but osquery achieves it with SQL, which is heavier than `rw_blueprint` requires.

#### Virtual tables: data generated on-the-fly, not stored

The key architectural insight from osquery's "Under the Hood": **most data is generated at query time through "Virtual Tables"**, not stored. A virtual table parses a file or calls a system API *when queried*. osquery uses SQLite's query engine but does *not* use SQLite for storage — it uses an embedded RocksDB only for event buffering and differential logging.

This maps directly to `rw_blueprint`'s probes: a probe should *generate* its fragment on demand (run `podman ps`, parse the output), not maintain a persistent store. The store is the *declared model* (git) and the *drift report* (output), not the probe's internal state.

#### Event publishers/subscribers: the push side, formalized

osquery's event system is the canonical "push" pattern: event publishers run in their own thread, generate a stream of events (e.g., inotify for file integrity monitoring), publish to subscribers, which filter and buffer into RocksDB. A query against an event-based table pulls from that buffer.

This is *exactly* the pull/push split `rw_blueprint` already identified: virtual tables = pull (collectors), event publishers = push (watchdogs). osquery validates that both halves coexist in one system with a shared vocabulary.

#### The "in-house vs. building" reality check

The Uptycs analysis is the critical cautionary finding: **running osquery in-house requires building everything around it** — fleet management, a data pipeline, storage, visualization, correlation, and ongoing tuning. "What starts as endpoint visibility quickly becomes an infrastructure problem." At enterprise scale, teams spend more time maintaining the platform than getting insight.

This is the decisive argument for `rw_blueprint`'s approach: **borrow the model, don't adopt the tool.** osquery is a C++ daemon with a SQL engine, a RocksDB store, and a plugin system — far heavier than a fleet of 5 read-only Python probes needs. The `rw_blueprint` probe registry captures the *model* (declarative observation, uniform output, on-demand generation, event publishers) without the *weight* (SQL engine, embedded DB, daemon lifecycle).

#### The OpenTelemetry agent-vs-gateway pattern is the deployment reference

The OpenTelemetry Collector research confirms the deployment shape: **agents collect locally (lightweight, near-source), gateways aggregate centrally (policy, credentials, processing)**. The transferable insight for `rw_blueprint`:

- Probes are the **agent** tier — lightweight, local, read-only, minimal processing.
- The reconciler is the **gateway** tier — central, holds the declared model, does the diff, enforces policy.
- **Credential isolation** — only the gateway (reconciler) holds write access to the declared model; probes never do.

This is the same "emit-is-untrusted / apply-is-gated" boundary, expressed in deployment terms.

#### The scheduler's "splay" is a heartbeat-relevant detail

osquery's scheduler adds a randomized "splay" so that a fleet of hosts doesn't run the same query at the exact same instant (which would cause a resource spike). For `rw_blueprint`'s heartbeat trains, this is a directly relevant detail: **jitter the probe schedule** so the hourly infra-health loop doesn't hammer all hosts simultaneously.

### Implications for rw_blueprint

1. **Borrow the model, don't adopt osquery** — the probe registry captures declarative observation + uniform output + on-demand generation without the SQL engine / embedded DB / daemon weight.
2. **Probes generate fragments on demand** — no persistent probe-side store; the declared model (git) and drift report (output) are the only stores.
3. **Probes = agent tier, reconciler = gateway tier** — credential isolation: only the reconciler writes the declared model.
4. **Jitter the heartbeat schedule** (splay) to avoid synchronized resource spikes.
5. **Event publishers = the future push/watchdog layer** — already validated by osquery's design.
