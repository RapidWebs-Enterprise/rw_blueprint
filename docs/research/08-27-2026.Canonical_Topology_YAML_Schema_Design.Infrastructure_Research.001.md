## Research Summary: Schema Design for a Canonical Topology YAML Source of Truth

**Source**: Synthesis of NetBox (IPAM/DCIM), C4 model, Shumoku, TopoViewer, and Marrow schemas; Pydantic v2 validation patterns  
**Date**: 2026-08-27  
**Research Category**: Infrastructure Research  
**Focus**: What a canonical `topology.yaml` must contain to serve as the single objective source of truth for humans, reproducibility tooling, and autonomous agents

### Key Findings

#### The schema must model five core entity types

A topology model that is simultaneously human-readable, agent-queryable, and IaC-generatable must capture five entity types, each with a stable identity and explicit relationships:

1. **Zones** — trust/security boundaries (e.g., `edge`, `infra`, `enterprise`, `dev`). Zones are the top-level grouping that drives firewall and segmentation reasoning.
2. **Nodes** — hosts, system containers, and physical devices. Each node belongs to exactly one zone.
3. **Services** — the running workloads (Caddy, Knot, Honcho, Matrix, RW Inference Engine). Services are hosted on nodes and expose ports.
4. **Links** — connectivity edges between nodes (e.g., Tailscale mesh, DNAT hops). Links carry protocol and direction.
5. **Dependencies** — directed edges between services (e.g., Honcho → pgvector). Dependencies drive startup ordering and blast-radius analysis.

#### Identity and reference integrity are the hard requirements

The single most important property of the schema is **referential integrity**: every `link`, `dependency`, and `service.host` must reference an entity that exists. A schema that permits dangling references produces exactly the drift the project exists to eliminate. This mandates:

- **Stable, unique identifiers** per entity (not display names, which drift).
- **Schema validation** that rejects dangling references at parse time.
- **Pydantic v2** as the validation layer (typed models, `model_validator` for cross-field checks).

#### The schema must be agent-diffable

For an LLM agent to propose changes as "the exact YAML diff," the schema must be:

- **Deterministic** — stable key ordering, no ambient state.
- **Flat enough to diff cleanly** — nested but not deeply; one entity per list item.
- **Self-describing** — a `schema_version` field and per-entity `id` so a diff is unambiguous.

#### Proposed canonical shape (v0.1)

```yaml
schema_version: "0.1"
metadata:
  name: rapidwebs-rwdn
  description: RapidWebs Distributed Network
  updated: 2026-08-27

zones:
  - id: edge
    name: Edge
    description: Public ingress boundary

nodes:
  - id: srv1
    zone: edge
    type: host
    provider: hetzner
    public_ip: 89.167.54.98
    tailscale_ip: 100.64.94.58

  - id: infra
    zone: infra
    type: container
    host: srv1
    tailscale_ip: 100.64.255.48

services:
  - id: caddy
    node: infra
    kind: reverse-proxy
    ports: [80, 443]
    managed_by: quadlet

  - id: honcho
    node: infra
    kind: application
    ports: [8000]
    depends_on: [pgvector]

links:
  - id: cloudflare-to-srv1
    from: cloudflare
    to: srv1
    protocol: https

dependencies:
  - from: honcho
    to: pgvector
    type: database
```

#### Design decisions grounded in prior art

| Decision | Rationale | Prior art |
|----------|-----------|-----------|
| `id` as stable key, `name` as display | Display names drift; IDs must not | NetBox slug convention |
| Zones as top-level grouping | Drives firewall/segmentation reasoning | C4 "context" + NetBox "site/region" |
| `managed_by` field on services | Distinguishes quadlet/systemd/host-managed — critical for reproducibility | Shumoku/TopoViewer "mapper" concept |
| `depends_on` as explicit edges | Enables startup ordering + blast-radius | C4 "relationship" + NetBox "dependency" |
| `schema_version` at root | Forward-compatible evolution | Every surveyed tool |

#### Open schema questions (deferred, not blocking)

- Whether `links` should carry a `direction` field or be implicitly bidirectional.
- Whether secrets/credentials belong in the model at all (leaning: **no** — secrets stay in the credential store, referenced by name only).
- Whether to model `ports` as a flat list or a structured `{port, protocol, public}` object.
