## Research Summary: Generator Architecture for YAML → Diagrams, Docs, and IaC Skeletons

**Source**: Convergence analysis of six independent projects (iacgen, semantic-diagrams, dockumentor, archspec, makejinja, diagrams-as-code); Jinja2 vs code-gen tradeoffs  
**Date**: 2026-08-27  
**Research Category**: Infrastructure Research  
**Focus**: The pipeline architecture that turns a canonical YAML model into generated artifacts, and the language/stack decision

### Key Findings

#### Six independent projects converged on the identical stack

The research surfaced six independent projects solving the "structured model → generated artifacts" problem, all of which converged on the same Python stack:

- **Typer** (CLI) · **Pydantic v2** (schema/validation) · **PyYAML** (parse) · **Jinja2** (templates) · **Rich** (output) · **pytest/ruff/mypy** (quality)

This convergence is strong evidence that the stack is the pragmatic sweet spot for this exact job class.

#### The pipeline is a linear, four-stage flow

```
topology.yaml  (canonical, git-versioned, agent-readable)
      │
      ├── 1. LOAD      — parse YAML (PyYAML safe_load)
      ├── 2. VALIDATE  — Pydantic v2 model + cross-field referential integrity
      ├── 3. EMIT      — Jinja2 templates → Mermaid / markdown / quadlet
      │
      └── 4. DIFF      — compare model against live state → drift report
```

Each stage is a pure function of the model, which makes the pipeline deterministic, testable, and safe for an agent to invoke.

#### Jinja2 vs code-gen: Jinja2 wins for this scope

| Approach | Pros | Cons | Verdict |
|----------|------|------|---------|
| **Jinja2 templates** | Declarative, human-editable, trivial to add a new output format | Template logic is limited; can get messy for complex transforms | ✅ Chosen |
| **Code-gen (emit Python/Go)** | Full programmatic control | Overkill for Mermaid/markdown/quadlet; harder to review | ❌ Rejected |

The outputs (Mermaid diagrams, markdown docs, quadlet units) are all *text templates* — the natural fit for Jinja2. Code-gen is warranted only if the engine later needs to emit arbitrary executable logic.

#### The language-agnostic contract is the key architectural insight

The one genuine alternative stack is **TypeScript** (Marrow, Shumoku, TopoViewer are all TS). But those are *interactive HTML renderers*, not agent-readable canonical models. The resolution:

- **Keep the YAML schema as the language-agnostic contract.**
- **Build the engine in Python** (the converged stack).
- **Bolt a TS renderer (Marrow/Shumoku) on later** as a presentation backend, without touching the model.

This decouples the *source of truth* (YAML) from the *presentation* (any renderer), which is the whole point.

#### Language/stack decision (finalized)

**Python 3.11+** with:

| Component | Choice | Rationale |
|-----------|--------|-----------|
| CLI | Typer | Type-hinted, Rich-integrated |
| Schema/validation | Pydantic v2 | Typed models, `model_validator` for referential integrity |
| Parse | PyYAML | `safe_load`, ubiquitous |
| Templates | Jinja2 | Declarative text emission |
| Output | Rich | Human-readable CLI feedback |
| Package/env | uv | 2026 standard, lockfile reproducibility |
| Quality | ruff + mypy (strict) + pytest | 2026 standard toolchain |

#### Emit targets (v0.1)

| Target | Template | Consumer |
|--------|----------|----------|
| Mermaid diagram | `topology.mmd.j2` | Humans (docs, README) |
| Markdown docs | `topology.md.j2` | Humans (never hand-edited) |
| Quadlet units | `*.container.j2` | Reproducibility (podman/systemd) |
| Incus profiles | `*.profile.j2` | Reproducibility (container layer) |
