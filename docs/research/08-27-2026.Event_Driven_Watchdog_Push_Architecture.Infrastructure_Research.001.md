## Research Summary: Event-Driven Watchdog (Push) Architecture for Real-Time Change Awareness

**Source**: podman/incus/systemd event APIs; inotify path-unit patterns; Kubernetes informer/watch model; reference code cloned to `~/.references/tfdrift` (watch mode) and `~/.references/driftguard`
**Date**: 2026-08-27
**Research Category**: Infrastructure Research
**Focus**: The "push" side of the observation loop — lightweight event hooks that emit normalized change events as they happen, complementing the pull/reconcile baseline

### Key Findings

#### Pull and push are complementary halves of one loop

The observation loop has two halves that are *not* competing options but complementary:

- **Pull (collectors)** — the reconciliation baseline. Catches drift that happened while nobody was watching (a service that died at 3am, an unplanned container that appeared). Level-triggered, eventually consistent.
- **Push (watchdogs)** — real-time awareness. Catches changes *as they happen* (a container restart, a config edit). Edge-triggered, near-real-time.

Pull alone = you only notice drift on the next poll. Push alone = you miss anything that changed before the watchdog was installed. Together they give both "eventually consistent reconciliation" and "near-real-time events."

#### The event primitives already exist in the stack

The push side does not require building a heavy agent on every host. The primitives are already present in the RWDN stack:

| Source | Mechanism | Fires on |
|--------|-----------|----------|
| `podman events` | container lifecycle stream | start/stop/restart/die |
| `incus events` | container lifecycle stream | start/stop/state change |
| systemd path units | inotify under the hood | config-file change |
| `tailscale status --json` | mesh state | peer join/leave |

Each watchdog is a **thin shim** that subscribes to one of these streams and re-emits a *normalized* event to the blueprint service.

#### The Kubernetes informer/watch model is the reference

Kubernetes' `watch` API is the canonical edge-triggered complement to its level-triggered reconcile loop. The transferable insight:

- **Watch is an optimization, not a requirement** — the reconcile loop works without it; watch just makes it faster. This is the argument for *deferring* push until the pull/reconcile loop is proven.
- **Events are untrusted, state is authoritative** — a watch event is a *hint* that something changed; the reconcile loop still re-reads full state to confirm. Events never replace the level-triggered baseline.

#### The critical security design: emit is untrusted, apply is gated

The single most important security property of the push side:

- **Emitting an event is untrusted and append-only.** A watchdog can *say* "Caddy restarted" but can never *write* to `topology.yaml`.
- **Applying a change is trusted and HITL-gated.** Only the agent (or human) writes to the declared model, and only after a human-in-the-loop gate.

This is the same blast-radius discipline as the pull side, applied to the event stream: the watchdog is a *reporter*, never an *actor*.

#### Normalized event shape

Every watchdog emits into the same normalized event shape, regardless of source:

```
{ source, event_type, entity, timestamp, payload }
```

- `source` — which watchdog (podman/incus/systemd/tailscale)
- `event_type` — start/stop/restart/config-change/peer-join
- `entity` — which node/service/link changed
- `timestamp` — when
- `payload` — source-specific detail

This normalization is what lets the blueprint service treat a podman restart and an incus restart as the *same kind of thing*.

#### tfdrift's watch mode is the minimal reference

`tfdrift` (cloned to `~/.references/tfdrift`) ships a `watch` mode — a continuous loop that re-runs drift detection on an interval. This is the *simplest* form of push (polling-as-watch), and it demonstrates that even a naive watch loop is useful. The event-driven watchdogs are a refinement of this, not a replacement.

### Implications for rw_blueprint

1. **Defer push** until the pull/reconcile loop is proven (per the Kubernetes "watch is an optimization" principle).
2. When built, implement watchdogs as **thin shims** over existing event streams (podman/incus/systemd/tailscale), not heavy agents.
3. Enforce the **emit-is-untrusted / apply-is-gated** security boundary.
4. Normalize all events into a **single event shape**.
5. Treat events as **hints** that trigger a reconcile pass, never as authoritative state.
