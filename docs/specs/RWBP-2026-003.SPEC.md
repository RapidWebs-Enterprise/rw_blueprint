## 1. Purpose

`rw_blueprint` v0.2.0 already declares a source of truth (`topology.yaml`), derives
artifacts from it (`generate`), observes live state (`probe`), and diffs declared vs.
observed (`reconcile`). But the tool is still consumed **only** as a human-facing CLI:
an agent cannot consume it as a typed capability, the drift report is a human-only Rich
table, and the reconciler reports *what* drifted without proposing *what to do about it*.

This SPEC defines the **"now" tier** from the ecosystem gap analysis — the three
capabilities that close the loop from "a source-of-truth engine" to "a self-healing
system's observe→propose half":

1. **An MCP server** (ADR-013) — exposing the four verbs (`validate`, `generate`,
   `probe`, `reconcile`) as typed, approval-gated tools plus read-only resources, so
   agents consume the tool as a capability surface rather than shelling out.
2. **Machine-readable output + deterministic exit codes** (ADR-017) — a versioned JSON
   drift report and exit-code contract (`0` clean / `1` drift / `2` error) that makes
   drift detection a pipeline gate and an agent-parseable artifact.
3. **A remediation proposal** (ADR-015) — a deterministic, minimal, never-auto-applied
   fix (YAML diff / JSON Patch) per drift item, with a blast-radius estimate and
   severity, as the input to the HITL gate.

The result is the concrete realization of RWDN Recovery Roadmap **P4 (Observe) → the
observe→propose half of P5 (Automate)** — without weakening the apply-is-gated boundary.

## 2. Scope

### 2.1 In Scope

- An **MCP server** (`rw-blueprint-mcp`) built on FastMCP (the official `mcp` Python
  SDK), exposing the four verbs as MCP tools and the declared model + drift report as
  read-only MCP resources.
- A **guarantee that CLI and MCP delegate to the same pure functions** (no logic fork).
- A **machine-readable drift report** — deterministic, versioned JSON emitted by
  `reconcile` via `--format json`.
- A **deterministic exit-code contract** — `0` clean, `1` drift/violation, `2` error —
  for CI gating.
- A **remediation proposal** — a per-drift-item minimal YAML diff (or JSON Patch) with a
  blast-radius estimate and severity, carried in the drift report under a `remediation`
  key. **Never auto-applied.**

### 2.2 Out of Scope

- **The P5 agent itself** — this layer produces the report + proposal the agent reads;
  the agent is a separate workstream.
- **Auto-remediation / apply** — the reconciler SHALL NOT apply changes. Applying a
  proposal is always HITL-gated (ADR-011, ADR-015).
- **Entry-points probe discovery** (ADR-014) — sequenced as a later "expansion" tier.
- **Schema migration command** (ADR-016) — sequenced as a later "next" tier.
- **Supply-chain security** (G3: SBOM/sigstore/SLSA/gitleaks/zizmor/trusted-publishing) —
  explicitly deferred by the user until internal adoption succeeds.
- **Layered configuration system** (ADR-018) — deferred; this SPEC's constants are
  hardcoded v0.1 defaults that the future config layer will override. The enterprise
  naming conventions (`rw_`/`RW_`, `__` nesting) are in force regardless.
- **The watch/wave 3 gaps** (G8–G13: watch mode, history, validate hints, layered views,
  fuzz tests, golden tests) — not blocking; noted for later.

### 2.3 Assumptions

- The four verbs' functions already exist and are pure/stateless (RWBP-2026-001,
  RWBP-2026-002).
- The MCP server uses **stdio transport** (local), which is the default and matches the
  "no hosted gateway" financial constraint in ADR-013.
- Consumers are human operators (CLI) and (future) agents (MCP), both on the same host.
- `mcp` SDK is pinned `>=1.27,<2` per ADR-013.

### 2.4 Constraints

- **Emit is untrusted, apply is gated** (ADR-011, ADR-015) — the MCP surface exposes
  read-only verbs and proposal output only; no write path to `topology.yaml`.
- **Single source of truth for logic** — CLI and MCP call the same functions; asserted by
  test (no logic fork).
- **Determinism** — identical inputs produce byte-identical JSON report (no ambient
  timestamps in the report body; timestamps belong in metadata, excluded from the
  determinism assertion).
- **Enterprise naming conventions** (ADR-018) — package `rw_blueprint`, MCP entry point
  `rw-blueprint-mcp`; future env vars use `RW_BLUEPRINT_` prefix with `__` nesting.
- MIT license; Python 3.11+; conforms to 2026 OSS repository structure standards.

## 3. Definitions and Acronyms

| Term | Definition |
|------|------------|
| **MCP** | Model Context Protocol — the open standard for exposing tools/resources to agents |
| **FastMCP** | The high-level `mcp.server.fastmcp` API (official `mcp` Python SDK) |
| **Tool** | An MCP-callable function with a typed JSON-Schema signature |
| **Resource** | An MCP-exposed read-only data source (URI-addressable) |
| **Remediation proposal** | A minimal, deterministic fix for one drift item, never auto-applied |
| **Blast-radius estimate** | A heuristic measure of how many entities a change could affect |
| **Exit-code contract** | `0` clean / `1` drift/violation / `2` error |
| **HITL** | Human In The Loop — a gated approval step |

## 4. Functional Requirements

### 4.1 Functional Requirement Format

**REQ-[ID]**: [Statement of behavior]
- **Given**: [Preconditions/context]
- **When**: [Trigger/event]
- **Then**: [Expected outcome/behavior]
- **Acceptance Criteria**:
  - [Measurable, testable criteria]

### 4.2 Requirements

**REQ-001**: The system SHALL expose an MCP server (`rw-blueprint-mcp`) that registers
the four verbs — `validate`, `generate`, `probe`, `reconcile` — as MCP tools, and the
declared model + drift report as read-only MCP resources.
- **Given**: An MCP host (Claude/Cursor/Goose/in-house harness) with the server configured
- **When**: The host lists tools and resources
- **Then**: The four tools and the resources are discoverable with typed JSON-Schema
  signatures
- **Acceptance Criteria**:
  - `validate`, `generate`, `probe`, `reconcile` appear as tools
  - `topology.yaml` (declared model) and the drift report appear as resources
  - Each tool's input/output JSON Schema is derived from the existing type hints

**REQ-002**: The MCP tools SHALL delegate to the same pure functions as the CLI — no
logic fork.
- **Given**: An invocation of a verb via CLI and via MCP with identical arguments
- **When**: Both are executed
- **Then**: Both produce identical results (the MCP tool wraps the same function)
- **Acceptance Criteria**:
  - A test asserts that `mcp.validate` and `cli.validate` call the same underlying
    function (or produce byte-identical output for identical input)
  - No verb is reimplemented inside the MCP adapter

**REQ-003**: The MCP surface SHALL preserve the emit-untrusted / apply-is-gated boundary —
all exposed tools are read-only with respect to the declared model.
- **Given**: The set of MCP tools
- **When**: An agent invokes any tool
- **Then**: No tool writes to `topology.yaml`; output is a report/artifact, never an
  in-place mutation
- **Acceptance Criteria**:
  - No MCP tool has a code path that writes to the declared model
  - A test enumerates all MCP tools and asserts none mutates the model

**REQ-004**: `reconcile` SHALL emit a deterministic, versioned JSON report via
`--format json`.
- **Given**: A valid topology and live-state
- **When**: `rw-blueprint reconcile <topology> <live> --format json` is invoked
- **Then**: A JSON document conforming to a `DriftReport` serialization is emitted,
  carrying a `report_version` field
- **Acceptance Criteria**:
  - JSON output parses into the report model
  - The document carries a `report_version` field
  - The Rich table remains the default when `--format` is omitted

**REQ-005**: The system SHALL return deterministic exit codes: `0` = clean, `1` = drift/
violation, `2` = error.
- **Given**: A `reconcile` invocation
- **When**: The command completes
- **Then**: The exit code reflects the outcome per the contract
- **Acceptance Criteria**:
  - No drift (after ignore rules) → exit `0`
  - Drift present → exit `1`
  - Invalid input / parse error → exit `2`

**REQ-006**: The reconciler SHALL emit, per drift item, a minimal, deterministic
remediation proposal (YAML diff or JSON Patch) that would restore declared/observed
agreement, each carrying a blast-radius estimate and severity. The proposal SHALL NOT be
auto-applied.
- **Given**: A drift report with findings
- **When**: The report is produced
- **Then**: Each non-ignored finding carries a `remediation` entry (action + minimal diff
  + blast-radius + severity), and no mutation occurs
- **Acceptance Criteria**:
  - A `missing` entity yields a proposal to add it (or flag the declaration as erroneous)
  - An `extra` entity yields a proposal to remove/ratify it
  - A `mismatched` field yields a minimal single-field diff (never full-document replacement)
  - The proposal is present in the report but never applied
  - Blast-radius is present and derived from the dependency graph

**REQ-007**: The JSON report schema SHALL carry a `report_version` field, independent of
the topology/live-state `schema_version`, so consumers can detect shape changes.
- **Given**: A serialized report
- **When**: It is parsed by a consumer
- **Then**: The consumer can read `report_version` to detect schema changes
- **Acceptance Criteria**:
  - `report_version` is present in every JSON report
  - It is independent of `topology.schema_version`

**REQ-008**: The system SHALL remain deterministic — identical declared + observed state
produces a byte-identical JSON report (excluding the `generated_at` timestamp, which is
metadata).
- **Given**: The same topology and live-state, run twice
- **When**: `--format json` is emitted twice
- **Then**: The two reports are byte-identical after normalizing `generated_at`
- **Acceptance Criteria**:
  - A golden-file test asserts byte-stability of the non-timestamp body

**REQ-009**: The MCP server SHALL remain a facade — it adds no new capability beyond the
four verbs and resources; any new verb is first added to the core, then surfaced.
- **Given**: The MCP server
- **When**: A capability is requested
- **Then**: It exists in the core first and is surfaced through MCP as a thin wrapper
- **Acceptance Criteria**:
  - The MCP module contains no business logic (only tool/resource registration + delegation)

## 5. Non-Functional Requirements

### 5.1 Performance Requirements
- **Response Time**: MCP tool dispatch SHALL add < 10 ms overhead over the underlying
  function for the batch CLI verbs.
- **Throughput**: Not applicable (request/response).
- **Scalability**: The JSON report SHALL remain valid for up to 1,000 drift findings.
- **Capacity**: Stateless; no persistent MCP session state beyond stdio.

### 5.2 Reliability Requirements
- **Availability**: N/A (local stdio).
- **Fault Tolerance**: An MCP tool that errors SHALL return a structured error result,
  never crash the server; the CLI exit-code contract SHALL be honored.
- **Recovery**: N/A (stateless).
- **Data Integrity**: The JSON report SHALL round-trip losslessly (serialize → parse →
  serialize byte-identical).

### 5.3 Security Requirements
- **Authentication**: N/A (local stdio; host controls invocation). The MCP server SHALL
  not listen on a network socket.
- **Authorization**: All MCP tools are read-only w.r.t. the model; remediation is
  proposal-only. MCP's approval-on-invocation default reinforces ADR-011.
- **Data Protection**: No secrets in tool signatures, resources, reports, or proposals.
- **Audit**: Drift findings and proposals SHALL be deterministic and descriptive.
- **Compliance**: MIT license; no regulated data.

### 5.4 Usability Requirements
- **Accessibility**: N/A (CLI + programmatic MCP).
- **Learnability**: A new user SHALL run `rw-blueprint reconcile ... --format json` with a
  single command.
- **Efficiency**: `--format json` + exit codes SHALL be the sole CI/agent integration path.
- **Satisfaction**: The JSON report SHALL name the exact entity, field, and proposed diff.

### 5.5 Operational Requirements
- **Deployability**: `rw-blueprint-mcp` console entry point registered in `pyproject.toml`;
  installable via `uv`/`pip`.
- **Maintainability**: Type-checked (mypy strict), linted (ruff), tested (pytest).
- **Monitorability**: The JSON report is a stable, versioned contract.
- **Portability**: Python 3.11+; stdio transport; no platform-specific code.

## 6. Interfaces

### 6.1 User Interfaces
CLI via Typer (existing) plus new flags: `reconcile --format {table,json}` and documented
exit codes. MCP via FastMCP (stdio).

### 6.2 Hardware Interfaces
None.

### 6.3 Software Interfaces
- **APIs**: `rw_blueprint.mcp` (FastMCP server) over the existing
  `rw_blueprint.generator` / `rw_blueprint.probes` / `rw_blueprint.reconciler` functions.
- **Data Formats**: JSON drift report (versioned); YAML/JSON-Patch remediation proposals;
  MCP JSON-RPC (handled by the SDK).
- **Communication Protocols**: stdio (MCP); local filesystem (CLI); SSH/Tailscale (probes,
  unchanged).
- **Dependencies**: `mcp>=1.27,<2` (additive); existing Pydantic v2, PyYAML, Typer, Rich.

## 7. Architecture Constraints

- **Language**: Python 3.11+ (consistent with ADR-003).
- **MCP**: FastMCP from the official `mcp` SDK; stdio transport; no logic fork (REQ-002).
- **Single source of truth**: CLI and MCP delegate to the same pure functions.
- **Determinism**: stable field ordering; no timestamps in the JSON body's deterministic
  core (metadata excluded from byte-stability assertion).
- **Security**: emit-untrusted/apply-gated preserved (ADR-011, ADR-015); no network socket.
- **Naming**: enterprise conventions per ADR-018 (`rw_blueprint` package, `rw-blueprint-mcp`
  entry point, `RW_BLUEPRINT_` env prefix for future config).

## 8. Acceptance Criteria

### 8.1 Test Scenarios
- MCP server registers 4 tools + 2 resources (REQ-001).
- MCP tools delegate to CLI functions (REQ-002).
- No MCP tool mutates the model (REQ-003).
- `--format json` emits versioned JSON (REQ-004).
- Exit codes 0/1/2 are correct (REQ-005).
- Remediation proposal is minimal, deterministic, and non-applied (REQ-006).
- `report_version` present and independent (REQ-007).
- Byte-stability golden test (REQ-008).
- MCP module contains no business logic (REQ-009).

### 8.2 Success Criteria
- All functional requirements have passing tests.
- `ruff check`, `ruff format --check`, `mypy` (strict), and `pytest` all pass.
- Coverage ≥ 80%.

### 8.3 Non-Functional Test Requirements
- Round-trip losslessness test for the JSON report.
- No-secret assertion on the report and proposal output.
- MCP-read-only assertion (enumerate tools → assert no mutation).
- Byte-determinism golden-file test.

## 9. Resolved Decisions

All open questions from v0.1.0 and the reverse-audit findings (G-1…G-10) are resolved. Full
rationale in `docs/specs/audits/synthesis-RWBP-2026-003.md`.

- **D-01**: Remediation format → JSON Patch (RFC 6902) under a `patch` key.
- **D-02**: Blast-radius → derived from declared `topology.dependencies`; `null` for `extra` entities.
- **D-03**: JSON/exit-code contract applies to `reconcile` only; `validate` keeps text output.
- **D-04**: MCP "drift report" resource = the report JSON *schema*; the report is a tool return value.
- **D-05**: `--fail-on` = severity threshold; outcome maps to exit 0/1/2 (errors → 2).
- **D-06**: `mismatched` remediation direction = observed authoritative; direction rendered explicitly.
- **D-07**: Verb classes: `validate`/`reconcile` pure; `generate` write-artifacts; `probe` network.
- **D-08**: MCP resource URI scheme `rw-blueprint://schema/<name>`.
- **D-09**: Remediation ordering `(entity_type, entity_id, field)`.
- **D-10**: Generic tool descriptions; no host-specific defaults.
- **D-11**: FastMCP registration smoke test (4 tools + 2 resources).
