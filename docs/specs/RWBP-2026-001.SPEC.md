## 1. Purpose

`rw_blueprint` is a declarative infrastructure **source-of-truth engine**. It solves the
problem that caused the RWDN post-data-loss drift: "what is true" currently lives in
multiple conflicting, hand-written markdown files that go stale within 30–60 days.

The engine establishes a single canonical, machine-readable YAML model of the
infrastructure topology, and **derives** all human-facing artifacts (diagrams, docs) and
machine-facing artifacts (IaC skeletons) from that one model. Because artifacts are
generated rather than hand-maintained, they cannot drift from the source of truth.

The model is also the **objective reality** that an autonomous agent reads, diffs, and
proposes changes against — the foundation for the self-healing agent described in the
RWDN Recovery Roadmap.

## 2. Scope

### 2.1 In Scope

- A canonical `topology.yaml` schema (versioned, validated, referentially complete).
- **Five first-class entity types** — zones, nodes, services, links, and dependencies —
  each with a stable unique `id`.
- A validation layer that rejects malformed, dangling-reference, duplicate-id, unknown-field,
  and unsupported-schema-version documents.
- A generator pipeline that emits, from the model:
  - Mermaid topology diagrams (human-facing).
  - Markdown documentation (human-facing).
  - IaC skeletons — podman quadlet units and Incus profiles (machine-facing).
- A CLI (`rw-blueprint`) exposing `validate` and `generate` commands.
- A Python package (`rw_blueprint`) with a stable public API.

### 2.2 Out of Scope

- **Rendering backends** (interactive HTML, live weathermaps) — deferred; the YAML schema
  is the language-agnostic contract, and Marrow/Shumoku/TopoViewer may be bolted on later.
- **The autonomous agent itself** — this project produces the *model* the agent reads; the
  agent is a separate, later workstream (RWDN Recovery Roadmap P5).
- **Secrets/credentials** — the model references secrets by name only; values live in the
  credential store. The schema SHALL NOT contain secret-bearing fields.
- **Live drift detection** — comparing the model against running state is a later phase
  (P4 Observe), not part of the initial engine.
- **Full container-image resolution** — the `image` field is a reference string; the engine
  does not pull or verify images.

### 2.3 Assumptions

- The topology is small-to-medium (one Hetzner host + a handful of system containers +
  ~6–12 services). No horizontal scale-out requirement in the near term.
- Consumers of the model are humans (via generated artifacts) and LLM agents (via the raw
  YAML), not a real-time control plane.
- Python 3.11+ is available on the build/run host.

### 2.4 Constraints

- The YAML schema MUST remain language-agnostic (it is the contract, not the engine).
- The engine MUST be deterministic: identical input produces identical output.
- No secrets in the model or in any generated artifact.
- MIT license; conforms to 2026 OSS repository structure standards.

## 3. Definitions and Acronyms

| Term | Definition |
|------|------------|
| **SoT** | Source of Truth — the single canonical model from which all else derives |
| **Topology** | The graph of zones, nodes, services, links, and dependencies |
| **Zone** | A trust/security boundary grouping nodes (e.g. `edge`, `infra`) |
| **Node** | A host, system container, external entity, or physical device |
| **Service** | A running workload hosted on a node, exposing ports |
| **Link** | A directed connectivity edge between two nodes |
| **Dependency** | A directed edge between two services (drives ordering + blast radius) |
| **IaC** | Infrastructure as Code |
| **Quadlet** | systemd-native declarative container units for podman |
| **Referential integrity** | Every reference resolves to an existing entity; no dangling refs |

## 4. Functional Requirements

### 4.1 Functional Requirement Format

**REQ-[ID]**: [Statement of behavior]
- **Given**: [Preconditions/context]
- **When**: [Trigger/event]
- **Then**: [Expected outcome/behavior]
- **Acceptance Criteria**:
  - [Measurable, testable criteria]

### 4.2 Requirements

**REQ-001**: The system SHALL define a canonical topology schema modeling five first-class
entity types — zones, nodes, services, links, and dependencies — each with a stable unique
`id`.
- **Given**: A topology document
- **When**: The document is parsed
- **Then**: Each entity is represented as a typed object with a unique `id`
- **Acceptance Criteria**:
  - A valid document parses into typed objects for all five entity types
  - Each entity exposes a unique `id` field
  - A `Dependency` is a first-class object (not a string field on `Service`)

**REQ-002**: The system SHALL enforce referential integrity at parse time.
- **Given**: A topology document containing a reference (node→zone, node→host,
  service→node, dependency→service, link→node)
- **When**: The document is validated
- **Then**: Any reference to a non-existent entity SHALL cause validation to fail with a
  descriptive error naming the offending entity and reference
- **Acceptance Criteria**:
  - A dangling zone reference is rejected
  - A dangling host reference is rejected
  - A dangling service-node reference is rejected
  - A dangling dependency reference (either endpoint) is rejected
  - A dangling link reference is rejected

**REQ-003**: The system SHALL reject duplicate `id` values within each entity type.
- **Given**: A topology document with two entities of the same type sharing an `id`
- **When**: The document is validated
- **Then**: Validation SHALL fail with a descriptive error
- **Acceptance Criteria**:
  - Duplicate ids are rejected for all five entity types (zone, node, service, link,
    dependency)

**REQ-004**: The system SHALL reject unknown fields (strict schema).
- **Given**: A topology document containing a field not defined by the schema
- **When**: The document is validated
- **Then**: Validation SHALL fail
- **Acceptance Criteria**:
  - A bogus field on any entity (including nested entities) is rejected

**REQ-005**: The system SHALL provide a `validate` command that loads a YAML file and
reports validity.
- **Given**: A path to a topology YAML file
- **When**: `rw-blueprint validate <path>` is invoked
- **Then**: The file is parsed and validated; a human-readable result is emitted
- **Acceptance Criteria**:
  - Valid file → exit code 0 and a success message
  - Invalid file → non-zero exit code and a descriptive error

**REQ-006**: The system SHALL provide a `generate` command that emits derived artifacts.
- **Given**: A valid topology YAML file and an output directory
- **When**: `rw-blueprint generate <path> --output <dir>` is invoked
- **Then**: Mermaid diagram(s), markdown doc(s), and IaC skeleton(s) are written to the
  output directory
- **Acceptance Criteria**:
  - A Mermaid file is produced
  - A markdown file is produced
  - Quadlet/Incus skeletons are produced for services/nodes marked as managed

**REQ-007**: The system SHALL be deterministic.
- **Given**: The same valid topology document
- **When**: `generate` is invoked twice
- **Then**: The output is byte-for-byte identical
- **Acceptance Criteria**:
  - Two runs produce identical output files

**REQ-008**: The system SHALL reject documents whose `schema_version` is not supported.
- **Given**: A topology document declaring a `schema_version` other than the supported
  version
- **When**: The document is validated
- **Then**: Validation SHALL fail with a descriptive "unsupported schema version" error
- **Acceptance Criteria**:
  - A document with `schema_version: "9.9"` is rejected
  - A document with the supported version parses

**REQ-009**: The system SHALL model service ports as structured objects.
- **Given**: A service exposing ports
- **When**: The document is parsed
- **Then**: Each port is represented as an object with `port` (container port), an optional
  `public` (host port, defaulting to `port`), and a `protocol` (`tcp`/`udp`, defaulting to
  `tcp`)
- **Acceptance Criteria**:
  - A port with only `port` set defaults `public` to `port` and `protocol` to `tcp`
  - A port with `public` ≠ `port` is preserved in generated IaC
  - A `udp` port is preserved in generated IaC

## 5. Non-Functional Requirements

### 5.1 Performance Requirements
- **Response Time**: `validate` and `generate` SHALL complete in under 1 second for a
  topology of ≤ 100 entities.
- **Throughput**: Not applicable (batch CLI, not a service).
- **Scalability**: The schema SHALL remain correct for topologies up to 1,000 entities.
- **Capacity**: No persistent state; stateless per-invocation.

### 5.2 Reliability Requirements
- **Availability**: N/A (CLI tool).
- **Fault Tolerance**: Invalid input SHALL produce a descriptive error, never a crash or
  partial output.
- **Recovery**: N/A (no mutable state).
- **Data Integrity**: The model SHALL round-trip losslessly (parse → dump → parse).

### 5.3 Security Requirements
- **Authentication**: N/A (local CLI).
- **Authorization**: N/A (local CLI).
- **Data Protection**: The model and generated artifacts SHALL NOT contain secrets.
- **Audit**: Validation errors SHALL be descriptive and deterministic.
- **Compliance**: MIT license; no regulated data.

### 5.4 Usability Requirements
- **Accessibility**: N/A (CLI).
- **Learnability**: A new user SHALL be able to validate a topology with a single command.
- **Efficiency**: `validate` + `generate` SHALL be the only two commands required.
- **Satisfaction**: Errors SHALL name the exact entity and reference at fault.

### 5.5 Operational Requirements
- **Deployability**: Installable via `uv`/`pip` from `pyproject.toml`.
- **Maintainability**: Type-checked (mypy strict), linted (ruff), tested (pytest).
- **Monitorability**: N/A (CLI).
- **Portability**: Python 3.11+; no platform-specific dependencies.

## 6. Interfaces

### 6.1 User Interfaces
CLI via Typer: `rw-blueprint validate <path>` and `rw-blueprint generate <path>`.

### 6.2 Hardware Interfaces
None.

### 6.3 Software Interfaces
- **APIs**: Python package `rw_blueprint.schema` exposing `Topology` and entity models;
  `rw_blueprint.generator` exposing emit functions.
- **Data Formats**: YAML input (canonical `topology.yaml`); Mermaid, Markdown, and
  quadlet/Incus text output.
- **Communication Protocols**: None (local filesystem).
- **Dependencies**: Pydantic v2, PyYAML, Jinja2, Typer, Rich.

## 7. Architecture Constraints

- **Language**: Python 3.11+ (finalized post-research; see ADR-003).
- **Schema**: Pydantic v2 models with `extra="forbid"` and cross-field validation.
- **Generator**: Jinja2 templates → Mermaid/markdown/quadlet (see ADR-004).
- **Determinism**: Stable field ordering; no ambient state; no timestamps in output.
- **Separation**: The YAML schema is the contract; the engine is one consumer of it.

## 8. Acceptance Criteria

### 8.1 Test Scenarios
- Valid topology parses (REQ-001).
- Each dangling-reference class is rejected (REQ-002).
- Duplicate ids rejected for all five entity types (REQ-003).
- Unknown fields rejected (REQ-004).
- `validate` and `generate` CLI commands function (REQ-005, REQ-006).
- Determinism across two runs (REQ-007).
- Unsupported `schema_version` rejected (REQ-008).
- Structured ports round-trip with protocol/public mapping (REQ-009).

### 8.2 Success Criteria
- All functional requirements have passing tests.
- `ruff check`, `ruff format --check`, `mypy` (strict), and `pytest` all pass.
- Coverage ≥ 80%.

### 8.3 Non-Functional Test Requirements
- Round-trip losslessness test (parse → dump → parse).
- No-secret assertion on generated output.

## 9. Resolved Decisions

The following open issues from v0.1.0 are now resolved (ratified in v0.2.0):

- **Link direction** (was §9 open issue): Links are **directed**, with direction implicit
  in the `from`/`to` fields. Mermaid renders `A --> B`. A bidirectional relationship is
  expressed as two `Link` entries. (See ADR-005 amendment.)
- **Ports shape** (was §9 open issue): Ports are **structured objects**
  (`{port, public?, protocol?}`), not a flat list. (See ADR-006.)
- **Dependency modeling** (forward-audit finding): Dependencies are **first-class
  entities** with their own `id`, symmetric with `Link`. (See ADR-005 amendment.)
